How Spring actually behaves

It is very easy to write a confident, plausible, wrong explanation of a Spring internal. So every feature here gets two things: a note written after reading the real source, and a lab module whose tests prove what the note claims. mvn test is the fact-checker.

How these notes are written

The order matters, because writing the prose first produces notes that sound right and are not. Read the implementation. Write a test that would fail if the claim were wrong in either direction. Only then write the explanation, with a pointer to the test underneath it.

That discipline has already caught three things this project had wrong: the value of SCHEDULED_ANNOTATION_PROCESSOR_BEAN_NAME changed in Framework 7, EventListenerMethodProcessor scans bean definitions so @Lazy beans still get their listeners, and two same-phase transactional listeners have no defined order.

Version under study

Spring Framework 7.0.9 and Spring Boot 4.1.1, on Java 21. Version-specific behaviour is called out rather than smoothed over, because that is usually the part that bites on an upgrade.
